# 公開しおり負荷試験レポート

実施日：2026年11月10日（Asia/Tokyo）

## 結論

**今回の試験条件で、公開しおりの本文APIは1,000リクエスト/秒を15秒間処理できた。15,000要求すべてが成功し、HTTPエラー・予定送信の欠落はともに0件だった。**

キャッシュHIT率は100%、p95は1ms、p99は2msだった。少なくとも今回確認した1,000リクエスト/秒について、設定した応答時間・エラーの基準を満たした。

2,000リクエスト/秒では予定送信の欠落が発生したため中止した。原因はアプリ側と計測側に切り分けられておらず、アプリの最大処理能力は未確定である。

## 試験条件

|項目|条件|
|---|---|
|対象|公開しおりの本文API `GET /api/shared/<token>`、単一URL|
|接続経路|`127.0.0.1:3001`。アプリ・DB・負荷生成を同じPCで実行|
|PC|12論理CPU、メモリー約16GB|
|実行環境|Node.js 26.13.0、pnpm 11.25.0、ローカルk6 1.8.2|
|閲覧条件|未ログイン、Cookieなし、応答本文4,665バイトのJSON|
|キャッシュ|Nodeプロセス内のメモリーキャッシュ。事前取得でウォームアップ済み|
|対象実装|匿名HIT時の公開状態のDB照合を省略。変更コミット：`d9c920a`|
|投入方法|一定レートのGET。1反復につき1要求、再試行なし|
|同時実行上限|100 VUs（仮想ユーザー）|
|計画|1,000→2,000→3,000→4,000→5,000リクエスト/秒、各15秒|
|実行予算|最大226,000要求・5分|
|中止条件|HTTP失敗、予定送信の欠落、p95/p99の基準超過|

応答時間の基準はp95が20ms、p99が100msを初期値とし、後続段階は1,000リクエスト/秒の基準値の3倍との大きい方とした。今回の1,000リクエスト/秒の結果では、後続段階も20ms・100msが基準となる。

- 両段階とも、測定前後のアプリプロセスは同一だった。
- p95は95%、p99は99%の要求が完了するまでの時間を示す。

## キャッシュとDB負荷の確認

キャッシュの再利用は、応答ヘッダー `X-Public-Cache: HIT` の件数で確認した。

利用中DBから分離した専用PostgreSQL DBによる関連テストでは、匿名の本文・共有写真のHIT時に、DB問い合わせの`pool.query`と接続取得の`pool.connect`がともに0回であることを確認した。関連するAPI統合・キャッシュ単体テスト38件は成功し、skipは0件だった。

実負荷試験の2,000件/秒段階でも、監視用接続自身を除いたアプリDB接続は全8サンプルで0本だった。

## 2,000件/秒で中止した理由

321件は、k6が予定した要求を開始できなかった件数（`dropped_iterations`）であり、HTTPエラーの件数ではない。計測器の処理遅れや、応答待ちによる同時実行枠の占有などで発生するため、この値だけでアプリの処理限界とは判断できない。

同サイズの4,665バイトを返す簡易応答への対照試験では、同時実行上限100・2,000件/秒を8秒間実行し、16,000要求すべて成功、p99は2ms、予定送信の欠落は0件だった。ただし、公開アプリの試験ではCPU・DBの監視処理も動いており、対照試験と実行条件が完全に一致しているわけではない。アプリ経路の一時遅延と計測側の待ちの内訳は未特定である。

中止条件に従い、3,000・4,000・5,000件/秒は実施していない。終了後はhealthと公開本文のHTTP 200、本文のキャッシュHIT、負荷生成プロセスの終了を確認した。

## 結果の適用範囲

今回確認できたのは、**同一PC内・単一URL・ウォームキャッシュの匿名本文APIに対する、15秒間の1,000 HTTP要求/秒の処理**である。

画像配信、ブラウザの描画、閲覧記録POST、複数URLによるキャッシュ追い出し、外部回線、長時間の継続負荷は今回の測定対象に含めていない。HTTP要求/秒を、そのままページ表示数/秒や同時利用者数へ換算しない。
