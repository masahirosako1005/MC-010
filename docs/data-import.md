## 必要な列と正規化

- 利用者の `ユーザーID` / `ユーザID` / `user_id` をファイルごとの明示対応で関連付ける。氏名をキーにしない。
- ヘッダーのBOM・空白・改行（`特典`と`獲得数`の間など）を正規化する。
- スタンプのスポット名／スタンプ名／獲得日時／獲得事実を保持する。
- タイムゾーンがない日時はAsia/Tokyo（+09:00）として検証しtimestamptzへ保存する。範囲外の日付は拒否する。
- 参加後の満足度を1〜5へ正規化し、良かった点を利用者全体の推薦タグへ使う。特定スポットの感想欄には流用しない。
- 前回同行者は提供列にないため推測しない。既定値「友人」、変更後は保存値を優先。
- 元の利用者IDは安定ハッシュ由来UUIDへ対応付ける。external_idもハッシュ由来。氏名、年齢、性別、LINE ID、登録時属性、要望本文は保存しない。

## メールと明示的デモ用別名

マスク済みメールはnullとして扱い、解除・推測・同一メールへの500人の割当をしない。`--with-demo-aliases` を指定した場合に限り、`sample@example.test` を実績があり未訪問候補も残る匿名利用者へ、`sample-empty@example.test` を履歴なし利用者へ決定的に割り当てる。元のemailや履歴は変更しない。これはデモ用仮メールであり、実ユーザーの連絡先ではない。

別の `db:seed` は `fixture:` 名前空間の4利用者と明確なデモ履歴を作る。demo01は初回パンフレット作成を試す追加アカウントで、seedでは冊子を作らない。取り込み先 `organizer:` 名前空間の履歴と混在させない。

## 実行と冪等性

```powershell
pnpm run db:migrate
pnpm run data:inspect -- C:\AI-Sprint\sample-data
pnpm run data:import -- C:\AI-Sprint\sample-data --with-demo-aliases
```

解析→必須列・キー・日時・メール・孤児・重複検証→全件transaction内upsert。1件でも不正なら全体rollback。匿名件数だけを出力する。ファイル内容＋取り込み変換版（現在v2）のハッシュをimport_runsへ記録し、同版・同内容は `already_imported`。履歴source_keyもUNIQUE。既存パンフレット・コメント・写真には触れない。

CSVを差し替える際は同じヘッダー契約を維持するか、adapterとテストを更新する。未知列へ意味を推測して自動対応しない。利用可能な未マスクメールが提供された場合は形式・重複を検証して初めてメール照合へ使う。

## 検証・復旧

実データのinspect、初回import、再importで件数が変わらず冪等になることをPostgreSQLで確認。単体テストはBOM/改行ヘッダー、キー、欠損ヘッダー、孤児、重複、未知スポット、不正日時、マスクメールを検証する。DB初期化は既存DBを削除せず空の別DBへmigration/seedする。写真を含む復旧はDBとUPLOAD_DIRの同時点バックアップを用いる。
