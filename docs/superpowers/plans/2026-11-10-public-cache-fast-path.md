# 公開キャッシュのDB照合削減と再測定

ユーザー指示: 公開しおりのキャッシュ利用時は公開状態のDB確認を省き、その後アクセス数の上限を再測定する。

## 方針

- 本文・共有写真の公開状態と掲載範囲のDB照合はキャッシュMISS時に行う。匿名のHITはDB問い合わせ0回とする。
- 本文キャッシュには非所有者向けバイトと内部用の所有者IDを一組で保持する。IDはHTTPへ追加しない。セッションの本人判定は維持し、作者向け本文とクーポンは毎回別に生成する。
- 共有写真は公開トークン・写真種別・写真IDをキーとし、公開状態・掲載範囲・安全な保存キーの照合とファイル読込をMISS内にまとめる。
- 既存の24時間・32MiB・128件・1件4MiB、同時読込の集約、更新時の全体失効、失効前の読込を再格納しない仕組みを維持する。
- `X-Public-Cache: HIT / MISS / COALESCED / BYPASS`を返す。本文・トークンをログへ記録する仕組みは追加しない。
- CLI/DB直接更新や別プロセスの変更後は、公開停止も含め手動クリア/アプリ再起動が必要となる。単一プロセス用の仕様として文書へ明記する。

## 実装と検証

1. 専用PostgreSQL DBとテスト側の一時画像領域で、匿名HITのSQL回数0、作者情報の分離、写真のキー分離、保存・写真変更・掲載解除・公開停止後の失効を検証する。利用中DBをテストで変更しない。
2. `src/server/public-content-cache.ts`、`src/server/sharing.ts`と関連テストだけを実装する。既存の別作業の変更を保持し、API本文の契約・画面・DB schemaを変えない。
3. 仕様・デザイン・README・検証記録のキャッシュ説明を更新する。Node 26と固定pnpmで対象テスト・check・buildを行い、3001番の対象アプリだけHidden再起動する。
4. 提供済み公開URLの匿名本文APIをウォームアップし、HITを実測する。前回と同じ同時実行100、各15秒で1,000→2,000→3,000→4,000→5,000req/s。最大226,000要求・5分。p95が20msまたは基準の3倍、p99が100msまたは基準の3倍を超えた段階、HTTP失敗、予定送信欠落で停止する。再起動が挟まった段階は除外する。
5. 終了後に最小の通常GETで配信を確認し、HIT数、SQL削減の根拠、処理量・遅延・中止理由を報告する。独立レビュー・全画面E2E・CSV再取り込みは今回の依頼へ拡張しない。
