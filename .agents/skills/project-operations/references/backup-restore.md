# DBバックアップ・復元

## 対象と事前条件

- 対象DB、PostgreSQLの接続先・バージョン、`UPLOAD_DIR`、アプリの起動元を特定する。設定値は秘密を含まないホスト・ポート・DB名・絶対パスだけを報告する。ソースの既定値を実際の稼働設定と決めつけない。
- 認証は既に用意された環境や認証経路を利用する。`DATABASE_URL`を表示したり、`--dbname`へパスワード付きURIを渡したりしない。秘密ファイルを開く必要がある場合は実行せず、利用者による認証環境の準備を求める。
- サーバーと互換性のある既存のPostgreSQLツールを使う。未導入ならその状態を報告し、無断でインストールしない。
- 保存先・復元先は絶対パスで確定し、アクセス権と空き容量を確認する。Git対象、公開静的フォルダー、元CSV置き場、稼働中のDBデータディレクトリには保存しない。
- パスの親子関係・重複・reparse pointを確認する。コピー元へコピー先が入り込む構成や、想定外のリンク先をたどる操作を避ける。既存世代・DB・写真は上書きしない。

## バックアップ

1. 世代ごとの新しい保存ディレクトリを用意する。DBダンプ、写真、保護されたmanifestを一組にし、全処理の成功まで未完了の世代として扱う。
2. DBと写真の整合性のため、未保存の画面入力は対象外であることを伝え、許可された停止時間内に本プロジェクトのアプリへの書き込みを止める。写真アップロード等の処理完了と、取り込みCLIなど他の書き込み元が停止していることも確認する。DBサービスと別アプリは止めない。
3. 写真コピーが完了するまで書き込み停止を保つ。停止できない場合、`pg_dump`単独のDB整合性と、DB・写真を一組にした整合性を区別し、完全な一組を取得できたと報告しない。
4. `pg_dump`のcustom形式で対象DB全体を直接ファイルへ保存する。表を固定列挙して新しい表を落とさない。写真参照、管理履歴、共有、クーポン、MCPキー、migration管理を含む。ロールなどクラスタ全体のオブジェクトはこの単一DBバックアップの対象外とする。
5. 各コマンドの終了コードを直後に確認する。ダンプを会話へ出さず、標準エラーにもSQLや個人情報が含まれ得るため保護されたファイルへ直接保存する。警告はログ確認手順に従って安全に要約する。
6. 同じ停止期間中に`UPLOAD_DIR`の写真を新しい保存先へコピーする。DBは画像実体を持たないため、DBだけの保存では写真付き復旧にならない。写真を表示せず、通常の保存形式であるUUID名のWebP以外のファイルがあればコピーを広げず確認する。
7. manifestへ取得時刻・タイムゾーン、秘密を除いたDB識別情報、ソースcommitとdirty状態、ツールバージョン、DBダンプのサイズとSHA-256、写真の件数・合計容量・各ファイルの相対キーとサイズ・SHA-256、書き込み停止区間、終了コードを保存する。写真キーの一覧は会話やGitへ出さない。
8. コピー元・コピー先の件数・ハッシュの一致、ダンプの存在と非ゼロサイズ、終了コードを確認する。ダンプ内部の目録を確認する場合も内容は保護先へ保存し、会話へ表示しない。これらはバックアップ作成の終了条件であり、復元成功の証明ではない。
9. 全工程が成功した世代だけを完了として扱う。アプリを停止した場合は成功・失敗にかかわらず元のDB・写真設定でHidden起動し、必要最小限のHTTP参照で配信を確認する。再起動に失敗したらそれも明示する。失敗世代の自動削除・世代ローテーションは行わない。

接続先と保存先を確定した後のPowerShell呼び出し例。変数は事前に設定し、認証情報は含めない。`$opsArchive`と`$opsDumpErrorLog`は新しい保護先の絶対パスにする。コマンド文字列を組み立てて`Invoke-Expression`へ渡さない。

```powershell
& (Join-Path $opsPgBin 'pg_dump.exe') --host=$opsDbHost --port=$opsDbPort --username=$opsDbUser --dbname=$opsSourceDb --no-password --format=custom --file=$opsArchive 2> $opsDumpErrorLog
$opsDumpExitCode = $LASTEXITCODE
```

`--no-password`で認証が失敗したらそこで止める。パスワード入力・認証設定変更へ自動的に進まない。ダンプと写真は暗号化されたことを意味せず、保存先の暗号化状況が不明なら未確認と報告する。

## 復元

1. 自分たちが作成した信頼できる世代を選び、manifestと保存ファイルのハッシュ・写真件数を照合する。ダンプはSQLを実行するため、出所不明のアーカイブをそのまま復元しない。
2. 原則、稼働中と異なる名前の新しい空DBと、新しい空の写真保存先を用意する。ホスト・ポート・DB名と絶対パスを照合し、稼働中の接続先・写真と異なること、DBにアプリの表がないことを確認してから実行する。DB名だけで別サーバーを同一視しない。
3. バックアップ内のロールを作り直さず、準備された復元用ロールを使う。`pg_restore --exit-on-error --single-transaction --no-owner --no-privileges`で指定した空DBへ復元する。`--clean`、`--create`、DB削除や既存表削除は使わない。
4. 復元の終了コードを直後に取得する。失敗したら既存DBへ切り替えたり、破壊的な再試行をしたりしない。エラー全文は表示せず、失敗した復元先と途中状態を報告する。
5. 同じ世代の写真を新しい保存先へ復元し、ハッシュ・件数を照合する。既定の`uploads`へ無条件にコピーしない。
6. 復元先のmigration状態、表ごとの件数、写真参照先のファイル有無を、値を公開しない集計で確認する。氏名・メール・回答・コメント・トークン・共有URLの実値をSELECT表示しない。最新コードに合わせたmigrationやseedは復元とは別の変更であり、自動実行しない。
7. セッション、共有URL、MCPキーの期限・失効状態も復元時点へ戻ることを説明する。復元で失効済みキーや停止済み共有が戻る場合がある。公開停止・キー失効・セッション削除は、必要な対象を具体化して依頼の範囲内で行う。
8. 接続先切替が依頼されていなければ、稼働中アプリの設定は変更せず復元先を報告して終える。切替が含まれる場合は、元のDB・写真の組を残し、復元したDBと写真の組へ揃えて切り替え、本プロジェクトだけをHidden再起動する。最小限のHTTP確認を行い、失敗時は元の組へ戻す。

```powershell
& (Join-Path $opsPgBin 'pg_restore.exe') --host=$opsRestoreHost --port=$opsRestorePort --username=$opsRestoreUser --dbname=$opsTargetDb --no-password --exit-on-error --single-transaction --no-owner --no-privileges $opsArchive 2> $opsRestoreErrorLog
$opsRestoreExitCode = $LASTEXITCODE
```

復元依頼に伴う終了コード・整合性確認と、アプリのAPI/E2Eテストや復元演習を区別する。後者は明示依頼時だけ実行し、専用DBと別の写真保存先を使う。バックアップ作成だけの依頼で復元を実行しない。
